# Phase 11 — mobile auth backend

**Status: backend and Android UI wiring implemented behind default-off flags; synthetic tests passed; not deployed or production-approved.** Real Android, Google, Neon and Vercel tests and independent security review are not complete. See `phase-11-mobile-auth-work-in-progress.md` for client setup and limitations.

## API contract

All mobile API routes require a configured canonical HTTPS `BETTER_AUTH_URL`; each request URL's origin must match it. They reject incoming browser `Origin` and `Cookie` headers. These checks are defense-in-depth and do **not** authenticate an application. Never put tokens, nonces, verifiers or session credentials in URLs, logs, analytics or crash reports.

- `POST /api/mobile-auth/start`: bounded JSON `{ "verifierHash": "..." }`; returns `{ "id": "...", "nonce": "..." }`. The verifier is a 32-byte CSPRNG secret generated by the native app, encoded canonical base64url. Its hash is SHA-256 of `openfind:mobile-auth:verifier:v1`, one zero byte, then the UTF-8 verifier. The database stores only the verifier and nonce hashes. Attempts expire after five minutes.
- `POST /api/mobile-auth/exchange`: bounded JSON `{ "id": "...", "verifier": "...", "token": "..." }`. Validates the Google signature, issuer, audience, applicable `azp`, expiration and server nonce; validates verifier and consumes the attempt by conditional DB update before issuing a Better Auth session. Returns `{ "session": "<signed bearer credential>" }` only after validation. The credential is a bearer secret, delivered in a body over HTTPS, never in a URL. Account mapping uses verified Google `sub`, not email-only matching.
- `GET /api/mobile-auth/session`: `Authorization: Bearer <session>`; returns `{ "authenticated": true }` for a valid signed, unexpired session. No profile or raw token is returned.
- `POST /api/mobile-auth/sign-out`: same Authorization header, JSON body `{}`. Verifies and revokes that exact session; returns `{ "signedOut": true }` only after database deletion is checked. Invalid or already-revoked credentials return 401. Storage/DB failures return 503, not a false success.
- `GET /api/mobile-auth/cleanup`: scheduled endpoint, requires `Authorization: Bearer <CRON_SECRET>`, never an app session. Removes bounded batches of expired attempts and old mobile rate-limit buckets. A full 5,000-row batch returns 503 to signal a possible backlog. Vercel cron is scheduled daily at 05:00 UTC; configure external monitoring/alerting and run additional authorized cleanup when saturated. A 204 means mobile API config is disabled.

Requests do not accept browser cookies. Start/exchange also reject Authorization. Responses use generic errors and no-store; 401 indicates rejected credentials, 429 a rate cap and 503 a configuration/infrastructure failure. The server does not claim a native app is genuine merely because it lacks Origin. No direct Better Auth public ID-token provider path is enabled. The issuance plugin is constructed privately per request and is not mounted on the public web auth route. Existing browser Origin checks remain unchanged.

## Configuration and safety

See `apps/web/.env.example`. `OPENFIND_MOBILE_AUTH_ENABLED` must be explicitly `true`, and HTTPS URL, database, Google Web/Android client IDs, auth secret, independent rate secret and independent cron secret must all be present before routes run. Do not use production user data while evaluating this flow. Do not paste environment files, bearer tokens or client secrets into chat. The Android ID and Web client ID are public identifiers; Android client setup must match package and signing certificate.

The shared fixed-window rate limiter uses the existing `rate_limit` table: separate per-operation global ceilings plus HMAC-pseudonymized client buckets. On Vercel, `x-real-ip` is trusted only under the Vercel runtime assumption; confirm header behavior and request URL forwarding against the actual ingress. Outside Vercel, client-provided forwarded headers are ignored and all clients share one unknown bucket. IP quotas are not app attestation; NAT, IPv6 address rotation and distributed attacks limit their effectiveness. A global cap can deny legitimate users. About one percent of accepted requests also trigger bounded opportunistic cleanup; the daily cron covers quiet periods. This probabilistic cleanup and the cron batch limit do not guarantee that all backlogs can be drained under an attack. Add reviewed Vercel Firewall/edge protections, quotas, alerting and load testing; configure monitoring for 503s and cleanup backlog. Shared rate buckets expire via cleanup, but this is not a guarantee against high-volume storage or traffic attacks.

## Failure and recovery boundaries

Conditional attempt consumption prevents duplicate winners in the tested setup, but it is not in the same transaction as account/session issuance. If later issuance fails, start a new attempt. When a session is created but cannot be returned, revocation is best-effort; a database or response-delivery failure can leave an orphan session until expiry or later revocation. Session expiry is seven days under existing auth configuration. Treat ambiguous response delivery as failure, never retry the same attempt expecting another session. Client-side secure storage and offline sign-out handling require real-device verification. Sessions are bearer credentials and theft allows use until revocation or expiry.

The sign-out adapter first verifies the signed credential, deletes the corresponding session via Better Auth's internal adapter, then checks that it is gone. This avoids treating Better Auth sign-out's swallowed deletion error as successful revocation. This pinned library integration must be re-reviewed on updates.

## Tests and remaining release gates

`pnpm --filter @openfind/web auth:mobile-backend-test` uses an isolated PGlite database and locally signed synthetic Google tokens. It checks request boundaries, existing web identity mapping, signed session validation, tampering, replay, five concurrent submissions with one winner, sign-out/revocation, DB/limiter failures, missing configuration, trusted IP handling and cleanup. PGlite exercises one embedded database and does not prove independent Neon contention. Existing web auth and origin regression tests must continue to pass.

Still required before deployment: independent Neon concurrency/failure tests; an HTTPS staging deployment with real Google Web/Android configuration; actual Vercel ingress/client-IP/cron verification; Android native compilation, SecureStore backup rules, real login/logout/cancellation/session restart tests; edge protection and monitoring; independent security/privacy review. Mobile sign-in remains disabled until those gates are met. No production-readiness or powered-off finding claim is made.

**Migration safety:** no new migration was added for this backend. It uses existing `mobile_auth_attempts` and Better Auth `rate_limit` tables. Arena and Windows migration sets have different filenames/history; never overwrite or apply one set to the other's database without review.
